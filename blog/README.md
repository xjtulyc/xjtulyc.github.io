# 博客维护与发布

入口为 `blog.html`，两个栏目为 `technical`（技术博客）与 `business`（商业判断）。2026-10-06，网站所有者授权持续研究、撰写中英文文章并自动公开上线，不需要逐篇重复确认。该授权不包括公开其他项目中的非公开实验、融资、客户、联系人或商业计划。

## 编辑标准

技术博客聚焦 AI4S 与 LLM 的重要论文和技术报告，每篇解决一个具体问题。顺序可以是：现象和最小基线、符号与假设、核心推导、算法和实现、可比较的证据、反例与适用边界。解释每个关键环节的输入输出、必要性及验收方式。公式应落到算法、张量、成本或评估协议；不能只是论文摘要的扩写。

AI4S 尤其检查科学先验、分子/患者/时间划分与泄漏、分布外泛化、不确定性，以及预测指标、实验验证与真实工作流收益的区别。LLM 尤其检查训练/后训练/推理目标、掩码/位置/缓存约定、公平 token 与计算预算、prefill/decode、显存与真实延迟。未执行的实验只能标为建议方案或推断，不得写成作者实测。

商业判断从中外头部公司可核验的动作出发，解释技术能力、成本与可靠性怎样改变客户需求、产品交付、价值链和竞争格局。给出替代解释、约束、6–24 个月的观察指标和可推翻判断的条件。融资、合同、潜在里程碑和收入分别表述；公司发布、基准成绩、客户采用和财务兑现不能混同。不写新闻汇编，不从私有投融资资料提取未公开事实。

优先实际阅读原始论文、技术报告、官方代码、产品文档、正式公告和财报。逐项核实数字、单位、版本、日期与来源；区分已知事实、公司自述、分析推断和情景预测。搜索摘要不能替代全文阅读。跨学科解释必要概念，保留技术深度。中英文应有相同事实、公式、图示含义、来源和不确定性。

参考科学空间的问题驱动、逐步推导和检验边界的写法，形成原创表达，不搬用句子或文章。实际读过的结构参考：[Attention 与 Softmax](https://www.spaces.ac.cn/archives/9019)、[Muon 指南](https://spaces.ac.cn/archives/11416/comment-page-1?replyTo=28963)。前者展示从异常到机制验证，后者强调公式与实现约定的对应。

每篇至少一幅有信息的图：原创流程、因果关系、机制对照或有来源和方法的真实数据图；不得制造实验曲线。原创示意图明确标注为分析/示意而非测量数据。双语 alt、图例、标题和图注必须齐全。优先小 SVG，单个本地图片不超过 500 KB。大图、论文 PDF、视频、数据集和模型权重用稳定的官方外链，不镜像到 GitHub Pages，不内嵌大段 base64。引用他人图需有许可、出处和文字替代说明。

## 文件格式

`blog/content/<slug>.json` 为发布源文件，格式为：

```json
{
  "slug": "meaningful-topic",
  "date": "YYYY-MM-DD",
  "category": "technical",
  "translations": {
    "zh": {"title": "标题", "summary": "纯文本摘要", "tags": ["主题"], "body": "完整中文 HTML 正文"},
    "en": {"title": "Title", "summary": "Plain-text summary", "tags": ["Topic"], "body": "Complete English HTML body"}
  },
  "sources": [{"title": "Original source title", "url": "https://example.org/source", "published": "YYYY-MM-DD", "accessed": "YYYY-MM-DD"}]
}
```

这只是格式说明，不是可发布文章。日期必须是真实发表日期；实质修订增加 `updated` 并在正文说明改动。`sources.published` 可省略或使用确切月份，`accessed` 必填。正文允许语义 HTML、公式的 sub/sup、代码、表格和图片，不允许脚本/iframe/内联样式。保留官方英文论文标题。图片路径为 `assets/<slug>-zh.svg` / `-en.svg` 或经核验的 HTTPS 外链。

每篇正文至少三个 h2。对应中英文标题最好使用相同 id，如 `id="mechanism"`；生成器增加 `zh-` / `en-` 前缀及目录。内部链接用 `href="#mechanism"`。代码转义 `<`、`>`、`&`；表格由生成器包裹滚动容器。

## 数学排版与配色

遵循 `blog/design-system.json` 的学术蓝灰规范。网站与原创图只使用深蓝导航、墨色正文、灰阶和一种低饱和蓝色强调；栏目与图表步骤用编号、字重和线型区分，不使用彩虹配色、渐变或彩色公式卡片。浅色主强调为 `#355C7D`，深色为 `#9AB7D3`；正文分别为 `#1F2933` / `#E4EAF0`。图中文字在手机宽度下仍应可读，优先纵向流程图。

所有数学表达使用学术风格的 KaTeX 排版，行内以 `\(...\)` 包裹，独立式以 `<div class="math-block">\[...\]</div>` 包裹；这些反斜杠写入 JSON 时须按 JSON 规则转义。变量斜体，单位、运算符与语义下标按数学规范直立；使用真正的分式、上下标和对齐推导，保持中英文公式一致。独立式居中，必要时编号，长式在公式容器内横向滚动。代码字段和伪代码仍用 code/pre，不作数学转换。

源文件可设置 `math: true`，生成器也会检测数学分隔符。文章页按 [KaTeX 官方文档](https://katex.org/docs/browser.html) 从外部 CDN 加载固定的 `0.19.0` 版本及 SRI 校验，输出 HTML 与无障碍 MathML，博客首页不加载数学运行时。字体和库不复制进仓库。发布前确认无 KaTeX 解析错误、字体加载正常、手机端分式上下标不截断、页面不溢出、深色公式对比足够；外部运行时不可用时保留 TeX 源码，不静默丢失公式。

正文及作者介绍都有静态 HTML 回退。文章页复用博客外壳和作者介绍，子目录资源前缀 `../`；`data-site-root` 保证导航正确。文章语言切换会同时更新整篇正文和 SEO 元数据，语言偏好沿用全站。无 JavaScript 时两种正文均可阅读。

## 发布步骤

1. 查看 git 状态和已发布索引，读取仓库外的研究/运行记录，检查是否重复选题或重复发布。保留用户工作，不擅自 stash、reset 或强推。若目标文件存在并发冲突，保留草稿并报告。
2. 在仓库外研究和起草，完成来源、公式、论证和双语核对。至少进行一次独立内容审阅；修正重要问题后才将定稿 JSON 与小型原创配图放入 `blog/content/`、`blog/assets/`。这些目录内的内容会公开。
3. 在仓库根目录运行 `python3 scripts/publish_blog.py`，再运行 `python3 scripts/publish_blog.py --check`。脚本只使用 Python 标准库，输出已经可部署的 HTML、`posts.json`、静态归档链接和 `sitemap.xml`。校验不代替事实与技术审阅。
4. 本地 HTTP 预览：检查桌面及 320–390px 手机、中文/英文切换、完整正文/图注/目录、深浅色、引用、子目录导航、搜索和栏目过滤。检查脚本错误、图片可用性、溢出、日期、canonical 和描述。保持五个主页面正常。
5. 只提交本次相关文件，按当前授权推送网站发布分支；不更改域名、部署密钥、访问控制、计费或其他项目。若推送结果不明，先检查远端提交，不盲目重复。
6. 核验 GitHub Pages 对本次提交部署成功，再访问公开文章确认内容、双语及图像。只有实际上线后才在私有运行记录中登记发布 URL、提交、主题、来源和核验结果。失败时保留可恢复状态，不把“已推送”当作“已上线”。

定时任务在北京时间每天 08:00、14:00、21:00 执行技术解读，11:00、17:00 执行商业判断。每轮最多发布一篇新文章或一次实质更新，不因缺乏合格材料而填充简讯，不批量补发错过的轮次。LLM 和 AI4S 保持持续覆盖；可用新的角度深入重要基础报告，但注明报告的真实时间，不把旧材料包装为最新新闻。

运行记录、失败原因、候选主题和个人偏好依据均留在仓库之外。定时任务通过 Codex 应用管理，不由网站或 GitHub Pages 执行。
